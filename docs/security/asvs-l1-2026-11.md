# OWASP ASVS Level 1: first-pass review of the API and its deployment (November 2026)

> **In short:** This is a first, code-reading pass over `backend/api` and the edge configuration in the repo (`render.yaml`, `frontend/mobile/vercel.json`, `frontend/console/next.config.js`), checked against OWASP ASVS 5.0.0 Level 1. Sign-in, sessions, tokens, webhooks, uploads, operator endpoints and error handling hold up. Every one of the 24 object endpoints we sampled checks ownership or scope in code. There are no critical or high findings. The main gaps are places where the handbook describes a control the code does not have: Postgres Row-Level Security, dependency auditing in CI, and CSP or security headers on the console and PWA. There are also some smaller hardening items. Handbook 13 §13.10 calls for a second pass by Rhythm Thakur and Manish Raje before the pilot.

## 2. Findings, by severity

No finding is critical or high: none lets an outside caller read or change another person's data on its own. The ranking reflects how much each finding weakens a control the handbook says we have, and how cheap it is to fix before the pilot.

### F1 (Medium, CONFIRMED): the Postgres Row-Level Security defence in depth is described but not built

- **Evidence:** Handbook 13 §13.4, handbook 10 (line 82), ADR-0006 and M0 §9 (an integration test "RLS session variable is set per transaction") all describe RLS on `orders`, `inventory_lots`, `partners` and `routes`, with `SET LOCAL app.hub_ids` set per transaction. No migration in `backend/api/migrations/versions/` has `ENABLE ROW LEVEL SECURITY` or `CREATE POLICY`. Nothing in `platform/db.py` sets `app.hub_ids`. `modules/identity/permissions.py:3` even says "once row-level security arrives".
- **Impact:** Isolation between hubs rests on the application checks alone. The sample in section 3 found them correct, but nothing catches a future missed check, and the documents claim more than exists.
- **Fix:** Pick one of two, and record the choice in a new ADR. (a) Build it: one migration per table with `ALTER TABLE … ENABLE ROW LEVEL SECURITY` and a policy `hub_id = ANY (current_setting('app.hub_ids', true)::uuid[])`, plus an admin bypass. In `platform/db.py`, set `SET LOCAL app.hub_ids` from the `Permit` at the start of each request transaction. Jobs need a separate role with `BYPASSRLS`, and the app's database role must not own the tables, since an owner bypasses RLS. (b) Defer it: change handbook 13 §13.4, handbook 10 and M0 §9 to say RLS is planned, not present, so the ASVS evidence stays honest. (b) is a docs-only PR and fits before the pilot. (a) is several migrations and needs care with PgBouncer, because `SET LOCAL` works only inside a transaction.

### F2 (Medium, CONFIRMED): no dependency vulnerability scanning in CI

- **Evidence:** `.github/workflows/ci.yml` has the jobs `detect`, `lint`, `secrets` (gitleaks, `:85-96`), `python`, `frontend` and `js-hints`. None runs `pip-audit`, `pnpm audit` or Trivy. `.github/` has no Renovate or Dependabot config. Handbook 13 §13.10 lists "Renovate updates, `pip-audit`, `pnpm audit`, Trivy image scan (planned)", and handbook 11 lists "OWASP ASVS L1 checklist, gitleaks, pip-audit, pnpm audit, Trivy image scan".
- **This pass:** `pip-audit` is not installed, and `uvx --offline pip-audit` is not cached, so no audit ran: it needs network access to the advisory database. The lockfiles are sound: `uv.lock` has hashes for every wheel (1,796 `sha256:` entries), every package comes from `pypi.org`, and the API image installs with `--locked`. `httpx2` (rather than `httpx`) is a documented choice (TDD §"Outbound HTTP", ADR-0024).
- **Fix:** Add a `deps-audit` job to `ci.yml`: `uv export --frozen --no-dev --no-hashes | uvx pip-audit -r - --strict`, and `pnpm audit --prod --audit-level=high`. Start it as non-blocking and make it blocking once it is clean. Add `renovate.json` (or `.github/dependabot.yml`) for `uv`, `pnpm`, Docker and GitHub Actions. Also add a `just audit` recipe so it can run locally.

### F3 (Medium, CONFIRMED): the console and PWA send no Content-Security-Policy or other security headers

- **Evidence:** `frontend/console/next.config.js:7-13` has no `headers()`. `frontend/console/proxy.js` adds only `x-gb-path`. `frontend/mobile/vercel.json` has only `routes`, with no `headers`. Handbook 13 §13.10 says "CSP and security headers on the console".
- **Impact:** The tokens are `HttpOnly`, so an XSS cannot steal them. But the pages are same-origin with `/v1/*`, so injected script could still send `X-GB-Client: web` requests as the signed-in staff member. Clickjacking is not blocked either (no `frame-ancestors` or `X-Frame-Options`).
- **Fix:** In `next.config.js`, add `async headers()` returning, for `/:path*`, a CSP (`default-src 'self'; frame-ancestors 'none'; object-src 'none'; base-uri 'self'`, with nonces for Next's inline scripts), `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin` and `Permissions-Policy`. Add the same set to `frontend/mobile/vercel.json` with a `headers` route or a `"headers"` block. Start with `Content-Security-Policy-Report-Only` for a week. This is Yash Salunkhe's folder.

### F4 (Low to medium; the missing limit is CONFIRMED, the impact PLAUSIBLE): no cap on request-body size

- **Evidence:** No middleware limits the body (`main.py:141-155`). uvicorn runs with defaults (`backend/api/Dockerfile:46`) and has no body limit of its own. Webhooks read the whole body before checking the signature (`modules/billing/router.py:330`, `modules/notifications/router.py:224`). `idempotency()` hashes the whole body (`platform/idempotency.py:91`). Pydantic `max_length` applies only after the full body has been read and parsed.
- **Impact:** An unauthenticated caller can send large bodies to the webhooks, `/auth/exchange` or `/auth/refresh`, on a 512 MB free instance. The real ceiling is whatever Cloudflare and Render's proxy allow; that is not in the repo, hence PLAUSIBLE.
- **Fix:** Add a small ASGI middleware in `platform/request_context.py`, or a new `platform/body_limit.py`. It rejects a `Content-Length` above 1 MiB with 413 `request.too_large` (problem+json) and counts streamed bytes for chunked bodies. Uploads go to R2 directly and never pass through the API, so 1 MiB is ample. The largest legitimate bodies are the intel ingest lists (`modules/intel_gateway/router.py:31`, up to 5,000 items), so either measure one or allow those operator routes a higher cap.

### F5 (Low; the code is CONFIRMED, the edge PLAUSIBLE): API responses carry no baseline security headers

- **Evidence:** Neither `RequestContextMiddleware` (`platform/request_context.py:41-49`) nor `main.py` adds `X-Content-Type-Options`, `Strict-Transport-Security`, `Cache-Control` or `X-Frame-Options`. `no-store` is set endpoint by endpoint (115 sites), so a new endpoint that forgets it has no default. HSTS could be set in Cloudflare's dashboard, but that is not visible from the repo.
- **Fix:** In `RequestContextMiddleware.send_with_request_id`, add `x-content-type-options: nosniff` and `x-frame-options: DENY` to every response. Add `cache-control: no-store` whenever the response has not set its own; the public pages set theirs (`platform/rate_limit.py:24`). Turn on HSTS at Cloudflare for `api.gharbasket.co.in` (or send `strict-transport-security: max-age=31536000` from the app when `APP_ENV` is not local), and write the setting down in handbook 12.

### F6 (Low, CONFIRMED): `JOBS_TOKEN` has no length check, and one token opens every operator endpoint

- **Evidence:** `JOBS_TOKEN` must be set (`platform/settings.py:307`), but it is not in the 32-byte list (`platform/settings.py:331-345`). The one token guards `/v1/ready`, every `/v1/internal/jobs/*` (`platform/jobs.py:348`) and the `/v1/internal/intel/*` writes (`modules/intel_gateway/router.py:18`). It is held by the Oracle VM scheduler, the mandi collector, GitHub Actions and the training jobs. Failed attempts are not rate-limited (`platform/operator.py:24-38`).
- **Fix:** Add `("JOBS_TOKEN", self.jobs_token)` to the minimum-length loop. Split the token in two: `JOBS_TOKEN` for the scheduler and CI, and `INTEL_INGEST_TOKEN` for the mandi collector and training uploads, each checked by its own dependency in `platform/operator.py`. A leaked collector token then cannot run jobs such as `purge_deleted_users` or `rekey_kyc_documents`. Also rate-limit failed tokens per address (`rate_limit.enforce` on a 401).

### F7 (Low, CONFIRMED): a revoked role keeps working until the access token expires (up to 15 minutes)

- **Evidence:** Roles are written into the access token when it is issued (`modules/identity/service.py:173-179`, `:205`). `revoke_role` deletes the grant but touches neither the session nor the deny-list (`modules/identity/staff_router.py:112-133`). Its summary says so: "reaches the person's token within 15 minutes". This was a deliberate choice, but ASVS expects authorisation changes to take effect promptly.
- **Fix:** When a grant is revoked, have `staff_admin.revoke_grant` write a Valkey key `gb:roles-changed:<user_id>` holding the current time, with a 15-minute TTL. `require_access_token` (`platform/auth.py:29-47`) then answers 401 `auth.invalid_token` to a token whose `iat` is older, so the app refreshes and gets the new roles. That is one extra `GET` per request; it could be batched with the `is_revoked` call. Partner suspension (`modules/partners/router.py:253-257`) should use the same mechanism.

### F8 (Low, CONFIRMED): the refresh cookie has no `__Secure-` prefix

- **Evidence:** `REFRESH_COOKIE = "gb_rt"` (`platform/web_session.py:20`; `frontend/console/lib/session.js:20`). It is set with `Secure` (`platform/web_session.py:60-68`), but without the prefix a non-secure subdomain or a network attacker could set a cookie of that name. `Path=/v1/auth` rules out `__Host-`, but `__Secure-` fits.
- **Fix:** Rename it to `__Secure-gb_rt` in both files. For one session lifetime (30 days), accept either name in `refresh` (`modules/identity/router.py:218`) and clear both in `clear_session_cookies`.

### F9 (Low; the code is CONFIRMED, the impact PLAUSIBLE): console sign-ins share one rate-limit counter

- **Evidence:** The console's server calls the API itself (`frontend/console/lib/auth-api.js:112-130`). It sends `x-gb-client: web` but neither `x-origin-secret` nor the visitor's address. `platform/client_ip.py:122-136` therefore counts every console sign-in against Vercel's egress address (`True-Client-IP` set by Cloudflare), within the 30-per-10-minutes exchange limit (`modules/identity/router.py:82`).
- **Impact:** This is an availability problem. Thirty staff sign-ins, or an attacker's, within 10 minutes from the same Vercel region lock the console's sign-in for everyone. It does not let anyone get round the per-phone limit.
- **Fix:** On the console's Vercel project, set `ORIGIN_SECRET` (the same value the PWA uses). In `lib/auth-api.js`, send `x-origin-secret` and `x-real-ip` (from Vercel's `x-real-ip` on the incoming request) on server-side API calls. After deploying, run the §13.3 check through the console as well.

### F10 (Low, CONFIRMED): the log scrubber masks less than the handbook says

- **Evidence:** `platform/logging.py:26-38` masks JWTs, bearer and basic credentials, DSN passwords and Indian mobile numbers. Handbook 13 §13.5 says "phone, address, names masked". No pattern covers names, addresses or e-mail addresses. The code mostly avoids logging them in the first place: the access log has the path only, never the query string (`platform/request_context.py:60-66`).
- **Fix:** Change the handbook row to say what is actually masked, and add the rule "never pass names, addresses or e-mails to a logger" to handbook 11's review checklist. Optionally, add an e-mail pattern to `_SCRUBBERS`, with a test next to the existing scrubber tests in `backend/api/tests/test_hardening.py`.

### F11 (Low, CONFIRMED): uploaded PDFs are kept without checking what they are

- **Evidence:** `ObjectStore.clean` re-encodes images but returns PDFs as they were uploaded (`platform/files.py:133-134`). The KYC claim then compares only the type and size that were signed (`modules/partners/kyc.py:159-167`). R2 serves files from its own origin, never ours, so the browser risk is small. Staff do open these files, though.
- **Fix:** In `clean`, read the first 5 bytes of any `application/pdf` object (a `Range` GET) and return `None` unless they are `%PDF-`. In `signed_get`, add `ResponseContentDisposition="attachment"` for PDFs.

### Informational (no change needed now; recorded for the second pass)

- **I1:** When Valkey is down, rate limits and the sign-out deny-list fail open (`platform/rate_limit.py:47-59`, `platform/revocations.py:36-43`). This is a documented decision in handbook 13 §13.3. It would be good to alert on the `rate_limit_skipped` and `revocation_check_skipped` log events, alongside the ADR-0033 probes.
- **I2:** Staging serves `/v1/docs` and `/v1/openapi.json` publicly (`platform/settings.py:458-460`). `/v1/health` reports the environment and commit (`platform/health.py:43-51`). The repo is public, so this is acceptable. Keep both off in prod: `docs_enabled` already turns them off.
- **I3:** The address used for rate limits on the direct path, `CLIENT_IP_SOURCE=header:true-client-ip` (`render.yaml:39-40`), relies on Cloudflare sitting in front of Render's `onrender.com` host too. Render does not document this (the comment at `render.yaml:31-33` says so). The control is the manual check in handbook 13 §13.3. Record the date and result of its last run there, and run it again after every change to the proxy or these variables.
- **I4:** The Idempotency-Key scope (`platform/idempotency.py:90`) depends on each handler declaring its auth dependency before `Idempotent`. Otherwise the scope is `anonymous`, and a stored response could be replayed before auth runs. All 95 idempotent handlers declare them in the right order (an AST scan made during this review). To make this robust, have `idempotency()` depend on `require_access_token` directly, and keep an `anonymous` variant only for unauthenticated routes, of which there are none today.
- **I5:** The console's `GET /v1/auth/session?end=1` signs the user out on a GET (`frontend/console/app/v1/auth/session/route.js:58-64`). With `SameSite=Lax`, another site can sign a staff member out by linking there. It is a nuisance only. It could become a `POST`, or check `Sec-Fetch-Site: same-origin`.
- **I6:** Sessions have a 30-day absolute lifetime (`modules/identity/service.py:40`) and no idle timeout. That is within ASVS L1. Review it for staff roles at L2.

Seven routes have no auth dependency at all: `/auth/exchange`, `/auth/refresh`, the two `/v1/public/*` pages (rate-limited, aggregate counts only, `null` under 5 households), and the Razorpay and WhatsApp webhooks (signed, see section 4). `/v1/health` is also open but returns no data. ## 4. Controls verified as working

- **CSRF for cookie sessions:** an unsafe method that arrives with only the access cookie needs `X-GB-Client: web`, and any `Origin` it sends must be in `WEB_ORIGINS` (`platform/auth.py:36-41`, `platform/web_session.py:34-40`). Sign-in that issues cookies runs the same check (`modules/identity/router.py:130-131`), as does a cookie refresh (`:217`). CORS allows only `https://localhost`, without credentials, so another site cannot send the custom header.
- **Webhooks:** Razorpay's is HMAC-SHA256 over the raw body, compared in constant time, before parsing (`modules/billing/router.py:327-332`). Each event is processed once per `event_id` (`:340-354`), and the top-up state machine refuses a second credit (`modules/billing/topups.py:140-141`). WhatsApp's uses `sha256=` HMAC plus the verify-token handshake (`modules/notifications/router.py:196-232`). With no secret configured, both answer 503 instead of accepting unsigned events.
- **Operator endpoints:** a bearer token compared in constant time (`platform/operator.py:28-38`). They are open only when `JOBS_TOKEN` is unset, which a deployed environment refuses at startup (`platform/settings.py:305-323`).
- **Rate limits:** exchange (per address, then per hashed phone after Firebase verification), refresh, presign (per user), data export, public pages, certificates and other per-user caps (`platform/rate_limit.py`; call sites in identity, files, partners, community, logistics, billing, analytics). The address comes only from `platform/client_ip.py`. It is never the leftmost `X-Forwarded-For` entry, and `x-origin-secret` is compared in constant time and refused when it appears twice (`platform/client_ip.py:100-119`). The PWA's Vercel route *sets*, and so overwrites, `x-origin-secret` (`frontend/mobile/vercel.json:7-13`).
- **Errors:** every exception type has a problem+json handler (`platform/errors.py:186-191`). Database errors become a generic 500, except for unstorable text, which is a 422 (`:174-183`). Startup errors never echo a secret (`hide_input_in_errors=True`, `platform/settings.py:115-117`). Tracing records route templates and SQL text without parameters, never headers or query strings (`platform/tracing.py:5`, `:331`).
- **Firebase key handling:** a refetch on an unknown `kid` is throttled to one a minute (`modules/identity/firebase.py:81-88`), and a failed fetch is a 503, never an accept.
